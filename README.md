# Agent-Shoppable Census

Can an AI agent buy a ring here?

A reproducible census of 100 of the largest US online sellers of engagement
rings and diamond jewelry, probing each domain for agent-readiness and sorting
the result into two tiers so that Shopify's default-on features do not inflate
the count.

Published by [Stienhardt](https://stienhardt.com/?utm_source=github&utm_medium=dataset_repository&utm_campaign=agent_shoppable_census),
a New York City lab-grown diamond and engagement ring seller. Stienhardt is one
of the 100 rows and is flagged as the
publisher in every table; its row is scored by the same script and the same
rubric as everyone else's.

* Latest results: [RESULTS-DRAFT.md](RESULTS-DRAFT.md)
* Domain list: [data/domains.csv](data/domains.csv)
* Raw evidence: [data/probe-results.jsonl](data/probe-results.jsonl) (one JSON object per domain: every status code, header of interest, snippet, and MCP handshake answer)
* One row per domain: [data/probe-summary.csv](data/probe-summary.csv)
* Probe script: [probe.py](probe.py)
* Results renderer: [make_results.py](make_results.py) (writes RESULTS-DRAFT.md from the run outputs)
* Run metadata: [data/run-meta.json](data/run-meta.json) (UTC start and finish, counts, probe version, User-Agent)
* Fixed September snapshot: [v0.2 release](https://github.com/JacobiusMakes/agent-shoppable-census/releases/tag/v0.2)
* Queryable summary tables: [Hugging Face dataset](https://huggingface.co/datasets/JacobiusMakes/agent-shoppable-census)

## The rubric

**Tier A, merchant-built.** The seller itself published something for agents.
Any one of:

* a server in the official MCP Registry (`registry.modelcontextprotocol.io`) whose
  website, remote, or repository URL is on the seller's domain, whose description
  names the domain, or whose name carries the seller's domain label;
* a live custom MCP endpoint at `/mcp` or one declared in `/.well-known/mcp.json`
  (a read-only `initialize` succeeds);
* an `agents.md` or `llms.txt` with real content that is not a platform template;
* an ACP (Agentic Commerce Protocol) checkout endpoint that answers at
  `/checkout_sessions` with a JSON or 405 response rather than a web page;
* a UCP (Universal Commerce Protocol) profile at `/.well-known/ucp` that is NOT
  the Shopify-hosted default.

**Tier B, platform-inherited.** Only what the platform provides to every store
by default. Any one of:

* a Shopify-hosted `/.well-known/ucp` (the JSON points at `myshopify.com`);
* an `agents.md` or `llms.txt` that carries a generator signature (Shopify's
  auto-generated "Store URL / Last Modified Time / Store Description" llms.txt,
  Shopify's auto-generated "Agent Instructions" agents.md, or a "Generated by
  Yoast SEO" llms.txt), or whose structure is shared by three or more unrelated
  stores in the sample (a platform or app template);
* schema.org `Product` or `Offer` JSON-LD emitted by the theme on the sampled
  product page or the homepage.

**Unreachable.** None of the above. The label follows the census brief and means
unreachable *for an agent*, not that the website is down. Three flags separate
the cases: `site_loaded` (the homepage returned 200 to our fetcher and was not a
bot wall), `blocked_automated_fetch` (403, 429, 503, a bot-wall page, or a
redirect to a bot-check host such as `validate.perfdrive.com`, recorded in
`bot_wall_host`), and `home_error` (the connection never completed: timeout,
reset, DNS, or TLS).

A domain with any Tier A evidence is Tier A even if it also has Tier B evidence.
Every reason is written out in the `tier_a_reasons` and `tier_b_reasons` columns.

Also recorded per domain: whether the sampled product page carries `Product`
JSON-LD with a GTIN or MPN, whether the checkout is Shopify, which AI crawlers
the site's robots.txt fully disallows, the MCP Registry `?search=` result for the
seller name, whether the remote endpoint of any matched registry entry answered a
read-only `initialize` and `tools/list` (`registry_remote_live`,
`registry_remote_endpoints`, `registry_remote_tools`), and whether the seller
appears in the community-maintained index of OpenAI's ChatGPT Apps directory.

## How to rerun

Requirements: Python 3.10 or newer. The script uses the standard library and
`requests` if it is installed (it falls back to `urllib` if not).

```
python probe.py                      # full run, 6 worker threads, 1 request/second/host
python make_results.py               # regenerate RESULTS-DRAFT.md from the run outputs
python probe.py --only kay.com,vrai.com   # re-probe a few rows and merge them into the last full run
python probe.py --only kay.com --no-merge # probe a subset and write only those rows (debugging; overwrites the outputs)
python probe.py --refresh-registry   # re-crawl the MCP Registry instead of using the cached snapshot
python probe.py --refresh-chatgpt-apps
python make_results.py --stdout      # print the results Markdown instead of writing the file
```

A `--only` re-probe keeps the full run's start and finish timestamps in
`data/run-meta.json`, appends a `reprobes` entry naming the rows and the time,
and each row carries its own `probed_at` in the evidence file. The rendered
results list any re-probes under "Run". Connection-level failures (timeout,
reset, DNS) are retried once after two seconds; HTTP status codes are never
retried.

For the monthly census: edit `data/domains.csv` if the list needs a correction,
run `python probe.py --refresh-registry` and then `python make_results.py`, and
commit the five changed files (`data/mcp-registry-snapshot.json`,
`data/probe-results.jsonl`, `data/probe-summary.csv`, `data/run-meta.json`,
`RESULTS-DRAFT.md`).

What a run does, in order:

1. Reads `data/domains.csv`.
2. Crawls the full MCP Registry (`/v0/servers?limit=100` with cursor paging) once
   and caches it to `data/mcp-registry-snapshot.json`. About 400 pages at one
   request per second, so a run that refreshes the registry spends roughly seven
   minutes on it before any domain is probed. Later runs reuse the snapshot unless
   `--refresh-registry` is passed.
3. Downloads the community ChatGPT Apps index README (cached to
   `data/awesome-chatgpt-apps-README.md`). If GitHub is unreachable, the column is
   marked unchecked and the run continues.
4. For each domain, fetches with a 15 second timeout and at most one request per
   second per host: the homepage, `/robots.txt`, `/.well-known/ucp`, `/agents.md`,
   `/llms.txt`, `/.well-known/mcp.json`, `/mcp` (GET), `/checkout_sessions` (GET),
   then one product page. The product page is found, in order, from: product-path
   links on the homepage (`/products/`, `/product/`, `/p/` and similar), the same
   on up to two collection pages, `ItemList` JSON-LD on those collection pages,
   the sitemap (a child sitemap the site itself names "product" is trusted), and
   last a heuristic for platforms whose product URLs carry no path hint (a long
   slug with a product word plus a numeric or SKU id or an `.html` ending). The
   method used is recorded per row as `product_discovery`. If the domain
   redirects to another domain, `final_host` and `redirected_offsite` say so and
   the evidence belongs to the destination site; if it redirects to a known
   bot-check host, the seller's own domain stays the base and the row is marked
   blocked. Bodies are decoded as UTF-8 when they are valid UTF-8, regardless of a
   missing charset header.
5. If, and only if, an endpoint advertises MCP (the `/mcp` GET answered like an
   MCP server, `/.well-known/mcp.json` declared an endpoint, the UCP profile
   declared one, or a matched MCP Registry entry declares a remote URL), the
   script POSTs a JSON-RPC `initialize` and a `tools/list`. Both are read-only
   discovery calls. Nothing else is ever POSTed.
6. Parses JSON-LD on the homepage and product page, classifies, and writes
   `data/probe-results.jsonl`, `data/probe-summary.csv`, and `data/run-meta.json`
   (start and finish timestamps in UTC, counts, the probe version, the User-Agent
   string).

The script never creates carts, checkouts, sessions, or accounts, never logs in,
and identifies itself with the User-Agent
`StienhardtAgentCensus/0.2 (read-only agent-readiness census; +https://stienhardt.com/agents.md)`.

A full run of 100 domains takes roughly ten to twenty minutes with six workers,
plus about seven minutes when the registry is refreshed. The 2026-09-03 run took
twenty minutes end to end (14:53 to 15:13 UTC): about seven for the registry
refresh and thirteen for the 100 domains. Hosts that never answer (connection
timeouts) cost the most, because each of their requests waits out the 15 second
timeout and is retried once. The exact start and finish of the latest run are in
`data/run-meta.json` and at the top of RESULTS-DRAFT.md.

Sources that were tried and could not be read by our tooling on 2026-09-02:
Forbes Vetted's "Best Places To Buy Engagement Rings" and "The Best Place To Buy
Diamonds" (HTTP 403 to the fetcher), Brillianteers' "Best Places to Buy Lab
Grown Diamond Engagement Rings Online" (HTTP 403), and Digital Commerce 360's
ranked jewelry list (membership paywall). JCK (jckonline.com), searched on both
days, reports on other bodies' rankings (for example Signet's placement on the
NRF Top 100) but publishes no ranked list of online jewelers that we could find,
so no domain carries a JCK source code.

Rules used when compiling the list:

* Marketplaces are excluded (Etsy, Amazon, eBay, 1stDibs, TheRealReal).
  Rare Carat is a diamond search marketplace that also completes sales; it is
  included because the brief asked for it, and its note says so.
* General merchandisers with jewelry departments are excluded (Costco, Walmart,
  Macy's, Target, Nordstrom, JCPenney, Kohl's, QVC, HSN, Saks). JTV (Jewelry
  Television, the retail brand of Multimedia Commerce Group, National Jeweler
  Supersellers No. 12) is included because it is jewelry-only and sells diamond
  and engagement rings online.
* Watch-only and fashion-jewelry-only sellers are excluded (Jomashop, Chrono24,
  Pandora, Swarovski, James Avery, Gorjana, Kendra Scott). Kendra Scott appeared
  in the 2026-09-02 draft list; it was replaced by JTV on 2026-09-03 because it
  is a fashion-first brand and JTV is the larger diamond seller.
* Insurers, labs, and trade bodies are not sellers and are excluded.
* Companies headquartered outside the US with no US e-commerce operation are
  excluded (Michael Hill, Birks, Paris Jewellers, Griffin, Ann-Louise, Charm).
  Luxury houses with US e-commerce that sells engagement rings are included.
* Lightbox (De Beers) is excluded because De Beers announced its closure in 2025.
* Simulant-focused sellers are excluded.
* Corporate parents that are not consumer storefronts are replaced by their
  consumer-facing domain (Almod Diamonds Ltd. becomes diamondsinternational.com;
  Sherwood Management becomes danielsjewelers.com; Nonantum Capital Partners,
  Supersellers No. 9, is represented by ross-simons.com, which it has owned since
  December 2020; Don Roberto Jewelers Inc. is donrobertojewelers.com, because the
  shorter donroberto.com is an unrelated domain).

The list is our best public-source approximation of "the 100 largest". No public
page ranks online engagement ring sellers by web sales, so the ordering inside the
file is by source tier (audited industry rankings, then traffic rankings, then
editorial lists, then well-known names), not a precise size order. Corrections
to the list are welcome; the CSV is the single place to change it.

## Stienhardt's own row, stated plainly

Stienhardt is in the table because it is a US online seller of engagement rings,
and it is flagged as the publisher so nobody mistakes the row for an independent
finding. What the probe records for stienhardt.com on the run date is the same
evidence it records for everyone: an MCP Registry listing
(`io.github.JacobiusMakes/stienhardt-store`, whose remote is the Shopify UCP
endpoint for the store, alongside the education server
`io.github.JacobiusMakes/diamond-mcp`, whose remote is the hosted helper at
`diamond-mcp.stienhardt.workers.dev`), a Shopify-hosted `/.well-known/ucp`
profile (Tier B on its own), an `agents.md`, and an `llms.txt`. The Tier A call
for the row rests on the registry listing and the two text files. Anyone can
check each of those at the URLs in the evidence file.

## What a journalist could verify themselves

Every claim in the tables is a public HTTP response. Open any Tier A row's
evidence in `data/probe-results.jsonl`, then visit the same URLs in a browser or
with curl: `https://<domain>/llms.txt`, `https://<domain>/agents.md`,
`https://<domain>/.well-known/ucp`, and
`https://registry.modelcontextprotocol.io/v0/servers?search=<seller>`. A
Shopify-hosted UCP profile is recognizable because the JSON points at a
`myshopify.com` address; a merchant-built one does not. For an MCP endpoint, the
`tools` list in the evidence file is what the server itself returned to a
standard `tools/list` request, and anyone can repeat that request with an MCP
client (for example `npx @modelcontextprotocol/inspector`). The run timestamps
are in `data/run-meta.json`, and re-running `python probe.py` reproduces the
whole table from scratch, so any row that has changed since our run will show
up as a difference, not a dispute. The domain list is a CSV with a cited source
code per row, so the "who counts as large" decision is inspectable too.

## Caveats, in one place

* Default-on Shopify features (a hosted UCP profile with an MCP endpoint, theme
  JSON-LD) would make a naive "agent-ready" count look large. That is exactly why
  Tier B exists and is reported separately.
* One product page is sampled per site, found automatically. A GTIN or MPN
  missing on that page does not prove it is missing on every page.
* Some sites block automated fetchers. A 403 to our User-Agent, a bot-wall page,
  or a redirect to a bot-check host is recorded as `blocked_automated_fetch` and
  the row is Unreachable; it does not mean the seller has nothing, only that an
  agent using plain HTTP could not see it.
* Some hosts never complete a connection at all (`home_error` records the
  timeout or reset). That is consistent with edge-level filtering but is not
  proof of it, so those rows are Unreachable with `blocked_automated_fetch` left
  false.
* Several large sites render product data client-side. Server-delivered HTML
  without JSON-LD is recorded as no JSON-LD, which is what a non-browser agent
  sees.
* Some themes emit Product JSON-LD that a strict parser rejects (a trailing
  comma, a raw control character). The probe retries such blocks after
  repairing those two defects and flags the row `product_jsonld_repaired`; a
  block that still fails is flagged `product_jsonld_malformed` and is not
  counted as present.
* ACP product feeds are submitted privately to OpenAI, so they cannot be detected
  from the outside. Only a public `/checkout_sessions` endpoint is probed.
* The ChatGPT Apps check uses a community-maintained index, not OpenAI's own
  directory, and matches by seller name or domain only.
* The MCP Registry match is by domain in URLs or description and by domain label
  in server names; a seller whose server is registered under an unrelated name
  would be missed by the automatic match and would need to be added by hand.
* The evidence file quotes what the sites served, verbatim, including text and
  punctuation that this repository's own prose avoids.

## Regenerating the third-party caches

Two large third-party files are not committed and are fetched by `probe.py` on each run:

* `data/mcp-registry-snapshot.json`, a full crawl of the official MCP Registry (about 21 MB).
* `data/awesome-chatgpt-apps-README.md`, the community ChatGPT apps index.

Delete the `data/` copies to force a refresh, or just run the probe; it refetches them when they
are missing.
